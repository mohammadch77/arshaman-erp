# راهنمای کار با Claude Code — Session، توکن و تکه‌بندی
## پروژه ERP آرشامان

> این سند جواب سه سؤال است: چطور کار را کوچیک کنم؟ چطور توکن کم بسوزانم؟ از کجا شروع کنم؟

---

# بخش ۱ — قانون طلایی تکه‌بندی

## تکه باید «کاملِ کوچیک» باشد، نه «نصفه‌ی کوچیک»

**معیار سنجش یک تکه‌ی درست:**
> بعد از تمام‌شدن تکه، باید بتوانی `commit` بزنی و چیزی که ساختی واقعاً کار کند.
> اگر نمی‌توانی commit بزنی، تکه‌ات نصفه است.

## برش عمودی، نه افقی

**غلط (افقی — نصفه):**
```
session ۱: نصف جدول سفارش
session ۲: بقیه جدول + نصف منطق   ← مجبوری کل session ۱ را دوباره بخوانی
session ۳: بقیه منطق
```

**درست (عمودی — کامل):**
```
session ۱: ساختار داده سفارش (migration + model + factory + یک تست)  ✓ commit
session ۲: ماشین وضعیت سفارش                                          ✓ commit
session ۳: اتصال ووکامرس                                              ✓ commit
```

هر تکه یک واحد مستقل که خودش کار می‌کند.

## اندازه درست یک تکه
- **کوچک‌ترین حد:** یک جدول با model و یک تست
- **بزرگ‌ترین حد:** یک قابلیت کامل که در ۳۰ تا ۹۰ دقیقه تمام شود
- **علامت اینکه تکه بزرگ است:** اگر پرامپت اولت بیش از ۴ تا «و» دارد، دو تکه‌اش کن

---

# بخش ۲ — چرا توکن می‌سوزد (درک ریشه‌ای)

## توکن از context می‌آید، نه از کد

هر پیام جدید در یک session، **کل تاریخچه مکالمه را دوباره می‌فرستد**. یعنی:

```
پیام ۱:  ۵ هزار توکن ورودی
پیام ۱۰: ۵۰ هزار توکن ورودی  (چون ۹ پیام قبلی هم همراهش می‌رود)
پیام ۳۰: ۱۵۰ هزار توکن ورودی (فاجعه)
```

**نتیجه:** session طولانی = گران. session کوتاه = ارزان. همین.

## دو نوع مصرف توکن
| نوع | چیست | کنترلش |
|---|---|---|
| ورودی (input) | تاریخچه مکالمه + فایل‌های خوانده‌شده | با `/clear` و session کوتاه |
| خروجی (output) | کدی که تولید می‌شود | با تکه کوچک و پرامپت دقیق |

ورودی معمولاً گران‌تر تمام می‌شود چون تجمعی است. پس **مدیریت context = بزرگ‌ترین صرفه‌جویی**.

---

# بخش ۳ — چرخه یک session سالم

```
۱. شروع session
   └─ «CLAUDE.md را بخوان»   ← Claude Code همه قواعد را یک‌بار می‌گیرد

۲. Plan mode
   └─ «برای [این تکه] نقشه بده، هنوز کد نزن»   ← نقشه ارزان است

۳. تأیید نقشه
   └─ نقشه را بخوان. اگر درست بود: «خوبه، پیاده کن»

۴. پیاده‌سازی (فایل به فایل)
   └─ migration → model → factory → test → action → کامپوننت Livewire + Blade view

۵. تست
   └─ php artisan test --filter=[ماژول]

۶. commit
   └─ git commit -m "feat: ..."

۷. آپدیت CLAUDE.md
   └─ تیک Epic تمام‌شده در بخش وضعیت

۸. /clear
   └─ context پاک می‌شود، session بعدی تمیز شروع می‌شود
```

**مدت هر session:** ۳۰ دقیقه تا حداکثر ۲ ساعت.

---

# بخش ۴ — نشانه‌های آلوده‌شدن context (کِی /clear بزنی)

اگر هر کدام از این‌ها را دیدی، فوراً commit و `/clear`:

- [ ] Claude Code قاعده‌ای از CLAUDE.md را فراموش کرد (مثلاً trait شرکت را نگذاشت)
- [ ] خودش را تکرار می‌کند یا کند شده
- [ ] کدی می‌نویسد که با کد قبلی همین session ناسازگار است
- [ ] بیش از یک ساعت در یک session هستی
- [ ] یک Epic تمام شد (همیشه بعد از هر Epic کلیر کن، حتی اگر همه‌چیز خوب است)

**قانون:** شک کردی؟ commit کن و clear بزن. context تمیز همیشه ارزان‌تر از context آلوده است.

---

# بخش ۵ — سه فایل حافظه که توکن را کم می‌کنند

به جای اینکه هر session قواعد را دوباره توضیح بدهی (توکن ورودی زیاد)، این سه فایل کار توضیح را یک‌بار انجام می‌دهند:

## CLAUDE.md
قانون اساسی. Claude Code هر session می‌خواندش. **دقیق‌تر باشد = توضیحات تو کوتاه‌تر = توکن کمتر.**
بخش «وضعیت فعلی» را بعد از هر Epic آپدیت کن — این‌طوری session بعدی نیازی به خواندن کل کد ندارد.

## BACKLOG.md
هر ایده خارج از تکه‌ی جاری اینجا می‌رود و همان‌جا می‌ماند. این جلوی مهم‌ترین عامل توکن‌سوزی را می‌گیرد: پریدن وسط کار به فیچر دیگر.

## DECISIONS.md
تصمیم‌های معماری با تاریخ و دلیل. وقتی سه هفته بعد یادت رفت چرا فلان کار را کردی، به جای اینکه از Claude Code بپرسی (توکن)، اینجا را می‌خوانی.

# بخش ۶ — الگوی پرامپت کم‌مصرف

## ساختار پرامپت خوب
```
[ارجاع به سند]  +  [مرز دقیق کار]  +  [چه چیزی نساز]  +  [تعریف تمام]
```

## مثال واقعی — Session 1
```
طبق CLAUDE.md، ماژول Core را شروع کن.

فقط این بخش:
- migration و model برای companies (فیلدها در CLAUDE.md بخش ۲)
- seeder پنج مجموعه واقعی + ستاد مشترک
- trait BelongsToCompany
- یک تست که global scope را ثابت کند

نساز: کامپوننت Livewire، نقش‌ها، هیچ ماژول دیگر.

تمام وقتی: migrate:fresh --seed کار کند و تست سبز باشد.
```

## چرا این کم‌مصرف است
- **ارجاع به CLAUDE.md** یعنی لازم نیست قواعد را در پرامپت تکرار کنی
- **«نساز»** جلوی تولید کد اضافه (توکن خروجی) را می‌گیرد
- **«تمام وقتی»** یعنی Claude Code می‌داند کِی بایستد، رفت‌وبرگشت اضافه نمی‌شود

# بخش ۷ — چه کاری با چه مدلی

همه کارها مدل قوی نمی‌خواهند. این تفکیک، چند برابر صرفه‌جویی است:

| نوع کار | مدل | مثال |
|---|---|---|
| مکانیکی و تکراری | سبک | CRUD ساده، فرم، migration معمولی، صفحه فهرست |
| نیازمند تفکیک منطق | قوی | ماشین وضعیت، محاسبه سود، تسهیم تایم‌شیت، سند حسابداری |

**قاعده:** مدل قوی را برای جاهایی نگه دار که یک اشتباه گران تمام می‌شود (منطق مالی). بقیه را سبک بزن.

---

# بخش ۸ — undo به جای اصلاح گفتگویی

## چرا اصلاح گفتگویی گران است
```
خروجی غلط → «نه، این‌طوری نه، آن‌طوری» → خروجی نیمه‌درست → «هنوز غلط» → ...
```
هر رفت‌وبرگشت، کل context را دوباره می‌فرستد. سه بار اصلاح = سه برابر توکن ورودی.

## راه درست
```
خروجی غلط → undo → پرامپت دقیق‌تر بنویس → خروجی درست
```
یک پرامپت دقیق، ارزان‌تر از سه اصلاح است.

---

# بخش ۹ — نقشه تکه‌بندی فاز ۱ (آماده استفاده)

هر ردیف یک session مستقل. بعد از هرکدام: تست، commit، آپدیت CLAUDE.md، clear.

| # | تکه | تمام وقتی |
|---|---|---|
| ۱ | شرکت‌ها + CompanyContext + trait | پنج مجموعه seed شوند، تست scope سبز |
| ۲ | نقش‌ها و دسترسی نقش×شرکت | تست دسترسی متقاطع سبز |
| ۳ | سوییچ شرکت + پوسته RTL | منو بر پایه نوع کسب‌وکار فیلتر شود |
| ۴ | ارز، نرخ، تقویم شمسی | resolver نرخ درست کار کند |
| ۵ | طرف‌حساب‌ها | CRUD با جستجو و فیلتر |
| ۶ | محصولات + بهای تمام‌شده + نوع تحویل | هشدار بهای نامشخص کار کند |
| ۷ | انبار پایه | موجودی = جمع حرکت‌ها |
| ۸ | سفارش: ساختار + ثبت دستی | محاسبه سود با snapshot درست |
| ۹ | سفارش: ماشین وضعیت | ترنزیشن نامعتبر رد شود |
| ۱۰ | اتصال ووکامرس | sync دوباره، تکراری نسازد |

**۱۰ session برای کل فاز ۱.** هر کدام مستقل، قابل commit، قابل بازبینی.

# بخش ۱۰ — اشتباهات رایج توکن‌سوزی

| اشتباه | نتیجه | راه‌حل |
|---|---|---|
| session طولانی بدون clear | توکن ورودی تصاعدی | بعد از هر Epic حتماً clear |
| «همه ماژول را بساز» | خروجی عظیم نیمه‌مصرف | فایل به فایل |
| اصلاح گفتگویی مکرر | context تکراری | undo + پرامپت دقیق |
| تکرار قواعد در هر پرامپت | ورودی زیاد | ارجاع به CLAUDE.md |
| پریدن وسط کار به فیچر دیگر | context شلوغ | BACKLOG.md |
| مدل قوی برای کار ساده | هزینه بی‌مورد | مدل سبک برای CRUD |
| نخواندن خروجی و اعتماد کامل | باگ دیرکشف مالی | کد مالی را خط به خط بخوان |

# بخش ۱۱ — هشدار ویژه فاز ۵ (حسابداری)

فازهای ۱ تا ۴ برای vibe coding عالی‌اند. اما در **فاز ۵ (حسابداری دوطرفه)**:

- «vibe» را کم کن، «review» را زیاد کن
- تست‌های تراز را **خودت** بنویس، نه Claude Code
- خروجی سند حسابداری را خط به خط بخوان
- توکن بیشتری می‌سوزد ولی یک سند نامتراز که ماه‌ها بعد کشف شود، کل اعتماد به سیستم را خراب می‌کند

اینجا جایی است که صرفه‌جویی توکن در اولویت دوم است؛ درستی در اولویت اول.

# بخش ۱۲ — اولین روز کاری

```
۱. مخزن Laravel را بساز (دستورات در IMPLEMENTATION_PLAYBOOK بخش ۰.۲)
۲. CLAUDE.md را در ریشه بگذار
۳. BACKLOG.md و DECISIONS.md خالی بساز
۴. Claude Code را باز کن
۵. اولین پرامپت:

   «CLAUDE.md را بخوان. سپس برای Session 1 (شرکت‌ها) 
    نقشه بده، هنوز کد نزن.»

۶. نقشه را بخوان، تأیید کن، پیاده کن
۷. تست، commit، آپدیت CLAUDE.md، clear
۸. Session 2
```

**همین. یک تکه در هر session، ده session تا پایان فاز ۱.**
