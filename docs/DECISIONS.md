## ۱۴۰۵ — پشته فنی نهایی: Livewire 3 + Blade + Mary UI + MySQL

**تصمیم:** به‌جای Vue 3 + Inertia.js + Vuetify 3 + PostgreSQL (نسخه اولیه سند طراحی)، پشته نهایی
Laravel 11 + Livewire 3 + Blade + Mary UI (Tailwind + daisyUI) + MySQL 8 شد.

**دلیل:** تصمیم کارفرما/تیم توسعه برای سادگی معماری (بدون لایه API جدا برای UI داخلی) و تطابق بهتر با محیط میزبانی (لاراگون).

**پیامد:** همه اسناد پروژه (`CLAUDE.md`, `THEME_STRUCTURE.md`, `IMPLEMENTATION_PLAYBOOK.md`, `PROJECT_01_AUTH.md`) با این پشته بازنویسی شدند.

## ۱۴۰۵ — جابه‌جایی فاز منابع انسانی به بلافاصله بعد از هسته

**تصمیم:** ماژول منابع انسانی (HR) — پرسنل، حضورغیاب، حقوق — به فاز ۲ منتقل شد (بلافاصله بعد از هسته)،
به‌جای جایگاه اصلی‌اش (فاز ۴، بعد از عملیات/مالی) در سند طراحی نسخه ۳.۰.

**دلیل:** درخواست صریح کارفرما.

**تناقض پیدا شده:** طبق بخش ۵ سند طراحی، محاسبه حقوق باید خودکار در ماژول هزینه‌ها ثبت شود. اما ماژول
هزینه‌ها (فاز ۴ جدید، فاز ۲ قدیم) بعد از HR ساخته می‌شود، پس این اتصال در لحظه ساخت HR ممکن نیست.

**راه‌حل انتخاب‌شده:** HR کامل ساخته می‌شود؛ نقطه اتصال به هزینه‌ها با `// TODO` صریح در کد علامت‌گذاری
می‌شود و در `BACKLOG.md` آیتم #1 ثبت شده. وقتی به فاز هزینه‌ها رسیدیم، یک Action وصل‌کننده می‌سازیم که
هم دوره‌های قبلی حقوق را عقب‌ماندگی جبران می‌کند (backfill) هم از آن به بعد خودکار وصل می‌ماند.

**فایده جانبی:** چون HR (فاز ۲) قبل از خدمات پروژه‌ای/تایم‌شیت (فاز ۵) ساخته می‌شود، نرخ ساعتی تایم‌شیت
از همان ابتدا می‌تواند از حقوق واقعی محاسبه شود — نیازی به دوره میانی «نرخ دستی موقت» (که در سند اصلی
پیش‌بینی شده بود) نیست.

## ۱۴۰۵ — قرارداد نام‌گذاری دیتابیس: نقش کامل روی هر FK

**تصمیم:** هر کلید خارجی، صرف‌نظر از این‌که ابهام واقعی دارد یا نه، نقش کامل خودش را در نام حمل می‌کند.
مهم‌ترین اثر: `company_id` در همه‌جا `owner_company_id` شد؛ `created_by`/`updated_by` همیشه با پسوند
`_user_id` می‌آیند.

**دلیل:** درخواست صریح کارفرما برای دیتابیسی که بدون نگاه‌کردن به کد قابل‌فهم باشد.

**جزئیات کامل:** `DATABASE_CONVENTIONS.md`.

**پیامد:** `schema_auth_mysql.sql` و trait اصلی `BelongsToCompany` در `CLAUDE.md` بازنویسی شدند. هر
migration بعدی از روز اول با این قرارداد نوشته می‌شود — بازگشت به `company_id` خام یک باگ سبک است.

## ۱۴۰۵ — بازنویسی نقشه ماژول HR برای تطابق کامل با سند طراحی

**تصمیم:** نسخه اول `PROJECT_02_HR.md` چند بند از بخش ۷ سند طراحی را ساده کرده یا از قلم انداخته بود
(اطلاعات قرارداد کارمند، پنل خودِ کارمند، جمع ماهانه کارکرد/غیبت، بیمه/مالیات/مزایا، فیش قابل‌مشاهده،
تسهیم حقوق بین شرکت‌ها). نسخه جدید خط‌به‌خط با سند تطبیق داده شد.

**دلیل:** کشف حین بررسی مشترک با کارفرما قبل از شروع پیاده‌سازی.

**پیامد:** Session 1 با فیلدهای قرارداد/تماس گسترش یافت؛ Session جدید ۴ (جمع ماهانه) اضافه شد؛
Session 6 (حقوق) کسورات واقعی گرفت؛ تسهیم بین شرکت‌ها آگاهانه به `BACKLOG.md` منتقل شد.

## ۱۴۰۵ — انتقال کل گروه CRM به فاز جدید (زودتر از فاز ۶ اصلی سند)

**تصمیم:** به درخواست صریح کارفرما، هر ۶ ماژول گروه CRM (مخاطبین، تعاملات، قیف فروش، RFM، کمپین،
تیکتینگ) به یک فاز جدید بلافاصله بعد از تکمیل هسته منتقل شدند، نه فقط ماژول قیف فروش که سند اصلی
مشخص کرده بود.

**دلیل:** درخواست کارفرما.

**تناقض پیدا‌شده:** نصف این ماژول‌ها (تعاملات، قیف فروش برای آرشامان، RFM) به داده‌ای وابسته‌اند که
هنوز نساخته‌ایم (سفارش فاز ۳، قرارداد فاز ۵).

**راه‌حل:** همان الگوی موفق `expense_posting_status` در HR — ساختار کامل + TODO صریح + BACKLOG برای
اتصال واقعی بعدی. کمپین/اتوماسیون هم فقط شبیه‌سازی‌شده (log) است چون کلید API تلگرام/پیامک هنوز نیست.

**پیامد:** `docs/PROJECT_03_CRM.md` و `docs/schema_crm_mysql.sql` ساخته شدند. فاز محصولات/سفارش/انبار
(قبلاً فاز ۳) و فازهای بعدی یک پله عقب رفتند.

## ۱۴۰۵ — ENUM نیتیو MySQL برای page_categories.category_key/pages.page_status

**تصمیم:** برخلاف قرارداد استاندارد پروژه (VARCHAR + CHECK دستی، بخش ۳.۲
`DATABASE_CONVENTIONS.md`)، این دو ستون ماژول SiteBuilder از نوع `ENUM`
نیتیو MySQL ساخته شدند.

**دلیل:** درخواست صریح کارفرما.

**پیامد:** جزئیات کامل + هزینه (migration سنگین‌تر برای افزودن مقدار جدید
در آینده) در `DATABASE_CONVENTIONS.md` بخش ۱۴ مستند شده. این یک استثنای
موضعی برای همین دو ستون است، نه تغییر قرارداد کلی پروژه.

## ۱۴۰۵ — دسترسی نوشتن operator به extra_css/extra_js صفحات SiteBuilder

**تصمیم:** برخلاف الگوی امنیتی معمول پروژه (کد قدرت‌بالا/تزریق‌پذیر معمولاً
محدود به `holding_admin`)، نقش `operator` هم اجازه ویرایش فیلدهای
`pages.extra_css`/`pages.extra_js` را دارد — کدی که مستقیم و بدون sanitize
به صفحه عمومی تزریق می‌شود.

**دلیل:** درخواست صریح کارفرما؛ این ریسک (XSS/CSS injection توسط یک
operator بدخواه یا بی‌احتیاط) آگاهانه پذیرفته شده است.

**پیامد:** `PagePolicy`/`CreatePage`/`UpdatePage` این دو فیلد را از قید
draft-only که روی بقیه فیلدهای operator اعمال می‌شود مستثنی می‌کنند —
operator حتی برای صفحه‌ای که «مالک» آن نیست (چون Page اساساً نویسنده
مستقل ندارد) این دو فیلد را می‌نویسد، دقیقاً مثل بقیه فیلدهای صفحه‌ی draft.
اگر بعداً این ریسک مشکل واقعی ایجاد کرد، اصلاح (محدودکردن به
`holding_admin`) باید به‌عنوان یک تصمیم جدید اینجا ثبت شود، نه فقط در کد
تغییر کند.

## ۱۴۰۵ — enum های کسب‌وکاری از این پس ENUM نیتیو MySQL، نه VARCHAR+CHECK

**تصمیم:** از ماژول انبار (فاز ۳) به بعد، enum های کسب‌وکاری بسته و
کنترل‌شده توسط توسعه‌دهنده باید ENUM نیتیو MySQL باشند، نه VARCHAR+CHECK
(که قرارداد قبلی پروژه بود). مقادیر باز که کاربر نهایی باید بتواند بدون
تغییر کد اضافه کند (مثل `shipments.carrier`) همچنان VARCHAR می‌مانند.

**دلیل:** درخواست صریح کارفرما.

**پیامد:** `DATABASE_CONVENTIONS.md` بخش ۳ به‌روزرسانی شد. ماژول‌های قبل
از این تاریخ (Auth، HR، Core، CRM) با قرارداد قدیم (VARCHAR+CHECK) باقی
می‌مانند؛ تبدیل عقب‌رونده آن‌ها در `BACKLOG.md` ثبت شده و به یک Session
جدا و محتاطانه موکول شده — قانون append-only (ترتیب مقادیر دست‌نخورده)
باید حین آن تبدیل رعایت شود.
